# Verification status and evidence

## Release 0.4.0 (approvals: ask, bypass, deny)

- Automated checks on the final tree: lint, typecheck, build, `git diff --check`, and
  327 of 339 fixture tests pass (10 skipped; the same 2 process-group reaping tests as
  in 0.3.0 fail only in the maintainers' Linux container, whose PID 1 leaves killed
  orphans as zombies; CI runs on macOS).
- New fixture coverage (`test/approvals.test.ts`): the RPC client holding approval
  requests open (bound, denial fallback, other requests still denied), request summaries
  and responses for all five approval methods, scope checks, mode resolution and
  installer persistence, ask mode through `codex_task_approve` (paused wall clock,
  accept, decline, timeout, cancel, file-change and permission requests), bypass, deny,
  per-job tightening, and the Claude Code dialog over a real MCP SDK client with
  elicitation (accept, decline, dismissal without reopening, no capability).
- An independent review of the approval code found seven defects, all fixed with
  regression tests that fail without the fix: a permission grant broader than what was
  shown (every sandbox entry is now listed, and an incomplete request is declined without
  asking), requests left pending after the turn ended, a fifth simultaneous request
  failing the job, unbounded run time when nobody answers, a cut command approved in
  full, invisible Unicode in request text, and a dialog orphaned by a cancelled tool call.
  The approve tool now has to echo the request summary, and the dialog preselects
  Decline.
- Every response the bridge can send (accept and decline for the v2 command, file-change
  and permission approvals and the v1 exec/patch approvals) validates against the JSON
  schemas generated by codex-cli 0.162.1; that check caught the v1 denial shape
  (`{denied: {rejection}}`), fixed before release.
- Claude Code behaviour taken from its documentation: MCP elicitation since 2.1.76, and
  `anthropic/requiresUserInteraction` forcing a confirmation on every call of a tool.
  Whether Claude Code shows elicitation dialogs from a server outside a tool call is not
  documented, so the bridge only opens them during `codex_task_wait` /
  `codex_task_status`.
- Not covered: a live approval with a signed-in Codex (it needs a model turn that asks for
  one), and the dialog in Claude Desktop or the VS Code extension.

## Release 0.3.0 (image-series resilience)

- Automated checks on the final tree: lint, typecheck, build, `git diff --check`, and 302
  of 314 fixture tests pass (10 skipped as before). The 2 that fail in the maintainers'
  Linux container fail identically on the unchanged 0.2.3 tree there: they assert that a
  killed schema-generator helper is gone, and that container's PID 1 leaves killed
  orphans as zombies. CI runs the suite on macOS.
- New fixture coverage (`test/image-series.test.ts`): per-job `timeout_s`, the bounded
  queue, `codex_task_wait`, incremental saving (`files_so_far`), `partial_files` after
  timeout, `TURN_FAILED` and cancel, thread-folder salvage (complete files only, older
  files ignored, nothing during shutdown), reference-image validation and `localImage`
  turn input, `aspect`, file metadata, error hints, the bounded and cached
  `codex_status`, and the installer's timeout persistence. An independent review of the
  diff found five defects (hints after a late cancel or deadline, no retry of a copy that
  failed once, queued image jobs reserving sessions at enqueue, salvage continuing during
  shutdown, the salvage window of resumed threads); all are fixed with regression tests
  that fail without the fix.
- **Schema check** with the official codex-cli 0.162.1 npm package: the generated stable
  schema yields continuity available and `localImage` turn input available.
- **Signed-out protocol check** with the same 0.162.1 package in a Linux container with
  no OpenAI access (isolated `HOME`/`CODEX_HOME`, no sign-in, no credentials), driven
  through the built server over MCP stdio: `codex_status` answered in about 0.1–0.2 s;
  `codex_image_generate` with one reference image, `aspect: "1:1"` and `timeout_s: 20`
  passed the thread policy check, `turn/start` with the `localImage` input was accepted
  and echoed in the user message item, Codex then retried "Reconnecting… waiting for
  network" (`responseStreamDisconnected`) and the job ended `TIMEOUT` with
  `likely_cause: "network"`, `retried_errors: 5` and `first_model_event_ms: null`. No
  image was generated and no quota was used.
- **Field observation** that motivated this release (reported by the user, not
  maintainer-verified): 0.2.3 with Codex 0.162.1 on macOS, about 220 image jobs over two
  days from two parallel Claude sessions, 9 failures (8 `TIMEOUT`, 1 `TURN_FAILED` with
  `turn_message_class: "network"`), mostly at the 300 s default with 2–3 images per job
  and during drops of a mobile hotspot; several already generated images had to be
  recovered from `~/.codex/generated_images` by hand.
- Not covered: live image generation with 0.3.0, whether the model actually uses
  reference images, and live salvage of real image events. These need a signed-in run.

## Live smoke (manual, not part of `npm test`)

```sh
npm run build
node scripts/smoke.mjs status
node scripts/smoke.mjs task
node scripts/smoke.mjs write
node scripts/smoke.mjs image --confirm-spend-one-image   # ONE real generation, no retry
```

Each run uses a git-ignored `.smoke/<uuid>/` folder: `workspace/` is the task `cwd` and
`images/` is the image output root for every mode, so smoke runs never write to
`~/codex-images`. All modes require the five tools to be listed; `status` also requires
`image_generate_enabled: true` with `image_output` pointing at that run's `images/`.
Sanitized results go to `.smoke/<uuid>/evidence.json`. This SDK-client smoke supplements,
but does not replace, a test through Claude Code itself.
